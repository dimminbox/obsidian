Поисковые операторы в ES можно сгруппировать по назначению.

Вот пример запроса:  
  {
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "тормозные колодки" } }
      ],
      "filter": [
        { "term": { "brand.raw": "Bosch" } },
        { "range": { "price": { "lte": 5000 } } }
      ],
      "must_not": [
        { "term": { "status": "discontinued" } }
      ]
    }
  }
}


##### Типы вхождений 

Определяют каким образом условие должно встречаться, чтобы документ подошёл для поиска
bool используется чтобы объеденить способы поиска (типы вхождений), используется AND

- must считает score для каждого найденного документа. Мы можем попробовать найти документы различными способами и взять наилучший. Для этого используется dis_max. По умолчанию он вернёт документы условия, которое лучше всего отработало, т.к. за это отвечает параметр tie_breaker, который по - умолчанию 0. Но его можно делать от 0 до 1 и тогда он будет учитывать более слабые результаты поиска, добавляя их в общий score.
- should - необязательное условие, но если документ релевантен, то наикдывается доп. значение в score
- must_not - не должно выполняться условие, не считает score
- filter - просто возвращает документы, которые соотвествуют условию, без подсчёта score. Поэтому используется для запросов, которые подбирают документы по заданным параметрам, не принимая в рассчёт их релевантность
  Все эти операторы - это всегда массивы
  
  
Nested живёт в query используется для поиска по полям с nested типом. Это объект

##### Типы запросов

- match - полнотекстовый поиск с применением алгоритма BM-25
- multi_match - это запрос сразу по нескольким полям. По сути это синтаксический сахар для несольких запросов. У нас есть возможность бустить значение score по отдельному полю, если в нём нашёлся искомый терм тем самым повышая значимость этого поля.
  Также мы можем использовать разные режимы рассчёта итогового скоро по разным полям:
	  {
		  "query": {
		    "multi_match": {
		      "query": "Bosch тормозные колодки",
		      "fields": ["title", "brand"],
		      "type": "cross_fields"/ "best_fields" / "most_fields"
		    }
		  }
		}

  1. best_fileds возьмёт лучший score из перечисленных полей
  2. most_fields возьмёт суммарный score из всех полей, где терм реально совпал. Используется когда одно и тоже содержание продублировано в разных полях.
  3. cross_fields -хитрый механизм, который считает итоговый score следующим образом.  Он строит статистику ценности того или иного терма. Первый терм - это Bosch и он считает сколько документов вообще содержат этот терм в полях title или brand, затем второй и т.д. Далее применяется принцип IDF , т.е. чем больше документов найдено по укзанному терму, тем он менее значимее для поиска и тем меньше у него score. Далее просто суммируются score всех термов. Такой подход позволяет получать справедливый score но требует большей нагрузки на ES
    
- term - точное совпадение без анализа, обычно используются keyword поля
- range - фильтр на диапозон (числа, даты):
	- `gte` — больше или равно (>=)
	- `lte` — меньше или равно (<=)
	- `gt` — больше (>)
	- `lt` — меньше (<)
- wildcard (search_name*, *search_name) - делает поиск по полям, которые начинаются или заканчиваются на поисковый терм, первый - сильно дешевле, т.к. ищет по отсортированным данным, вьторой - просто лопатит все данные поля.
- fuzzy использутеся для опечаток. Применяется специальный алгоритм, который допускает опечатки в поисковом слове, чем больше поисковое слово, тем больше допускается опечаток.
	{
	  "query": {
	    "fuzzy": {
	      "NAME": {
	        "value": "berkingo",
	        "fuzziness": "AUTO" // количество допущенных ошибок, AUTO от 0 до 2 в зависимости от длины слова
	      }
	    }
	  },
	  "_source": [
	    "NAME"
	  ]
	}
- prefix vs edge n-gram -механизмы для автокомплита. Первый поиск по префику, т.е. вся работы выполняется в момент запроса, второй означает, что вся работа идёт при переиндексации, т.е. индекс становится больше но при этом содержит токены для автокомплита.
  
###### Подсказки

В ES есть механизм подсказок, то есть на основании поля text оператор suggestion пытается получить похожие значения, которые встречаются в поле.
Например, 
	{
		 "suggest": {
		    "text": "ручка",
		    "correction": {
		      "term": {
		        "field": "SEARCH.SUGGEST", //поле
		        "analyzer": "SUGGEST_ANALYZER", //анализатор
		        "suggest_mode": "always",
		        "max_edits": 1, //по сути максимальное количество опечаток
		        "size": 2 //количество вариантов при выводе
		      }
	    }
	  }
