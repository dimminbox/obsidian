#### merge.conflictStyle zdiff3

При мерже иногда возникают конфликты, и в файле появляются строки похожие на:
<<<<<<< HEAD x = 2 
======= x = 3 
\>>>>>>> feature

Не понтяно что было до конфликта. Решение проблемы - это настройка 
git config --global merge.conflictStyle zdiff3 которая добавляет строку, которая было до конфликта:

<<<<<<< HEAD
x = 2
||||||| исходная версия
 x = 1
=======
x = 3
\>>>>>>> feature


#### git checkout theirs, ours

Конфликты можно разрешить, выбрав нужныую версию файла - ours (то, что в HEAD) и theirs. Допустим, мы делаем rebase ветки feature из ветки master, т.е. недостающие коммиты из feature должны встать после коммитов из master в ветку feature. Для этого мы должны испльзовать - git checkout theirs filename т.е. "опорная" ветка у нас master

Если мы делает merge master в feature мы должны выбрать команду git checkout ours filename т.к. "опорная" ветка - feature. 

Также можно сделать так, чтобы при merge выбирались конфликтные файлы ours,theirs. Это делается через команду - git merge -X ours/theirs master.
Иногда требуется сделать merge одной ветки в другую при этом не затронуть файлы в оригинальной ветке.  Для этого команда - git merge -s ours master, где master - имя вливаемой ветки.

#### git diff --check

Ищет маркеры конфликтов в файлах и выдаёт название файла и номер строки. Откатится назада к состоянию сразу после rebase - git checkout --merge filename.

#### git rerere
Иногда возникают ситуации когда нужно разрешать один и тот же конфликт много раз (например, делать rebase на много веток) или в процессе разрешения конфликтов решили сделать git rebase --abort приходится заново разрешать конфликты. Для этого придумали команду rerere, которая запонимает разрешенный конфликт. Кофликт считается разрешённым если сделан git commit или git rebase --continue. Для этого можно включить настройку - git config --global rerere.enabled true и при каждом следующем таком же конфликте git будет сам разрешать его. 

Если решение было неудачным то можно его забыть git rerere forget filename. Посмотреть, что запомнилось - git rerere status.

#### git merge --no-commit

Иногда требуется не сливать ветку а увидеть файлы до коммита. Эта команда сливает файлы и добавляет изменения в индекс через git add но не делает commit. Это позволяет посмотреть на итоговый код до коммита. 

После получения конфликтов полезным будет получить список коммитов, которые привели к конфликтам. Это делается командой - git log --merge --left-right --oneline, она показывает чьи правки столкнулись.
