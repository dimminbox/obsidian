Если выполнить git rebase main на ветке dev, то команда пересоздаёт локальные коммиты ветки dev, которых нет в main поверх последнего коммита из локальной ветки main.
#### git rebase -i 

перебазирует коммиты внутри ветки, например, git rebase -i --root переделывает коммиты, а именно, доступны следующие действия:
- pick - оставить как есть
- reword - поменять сообщение в коммите
- edit - остановиться на коммите, разбить или что - то изменить
- squash - влить в предыдущий
- fixup  -влить в преидыдущий, сообщение выборосить
- drop - удалить коммит
- exec - выполнить комманду после коммита

Чтобы разбить коммит на 2 части нужно сделать git rebase и выбрать edit напротив нужного коммита, дальше сделать git reset HEAD^ чтобы удалить изменения из индекса. Потом нужно добавить каждое изменение через git add -p.

Чтобы завершить rebase нужно сделать git rebase --continue

#### git rebase --onto

Команда, которая позволяет указать какие коммиты откуда брать и куда ставить в то время как git rebase просто ставит все локальные коммиты ветки поверх последнего коммита локальной ветки.

Например, git rebase --onto master hash dev  - берёт коммиты из ветки dev после указанного с хэшом (его не включая). Далее ставит их после последнего коммита ветки master. В итоге получается в ветку dev последний коммит ветки master и локальные коммиты из ветки dev после указанного хэша. 

Таким образом происходит ручное управление тем, какие локальные коммиты нужно поместить поверх master в ветку dev. Команда пересоздаёт коммиты, то есть у них будут новые хэши.

##### git rebase --update-refs

Допустим у нас есть три ветки - master, ветка dev растёт из master, feature растёт из dev. У веток dev, feature открыты MR с веткой master, которая ушла далеко вперёд. Мы делает rebase на ветке dev и она теперь содержит свои коммиты поверх тех, что были в master и это нормально, но проблема в том, что feature перестаёт быть продолжением dev, т.к. указывает на старые коммиты, их больше нет, теперь они имеют другие хэши. 

Команда git rebase --update-refs master на нижней ветке feature пересоберёт все ветки включая feature и промежуточную dev. Команду нужно запускать на ветке, которая дальше всех от master.

#### git rebase --exec "command" branch

Запускает команду после rebase после каждого коммита и если она завершилась успешно, то rebase применится. Если же команда упала, то git пишет "execution failed" и останавливает rebase и показывает коммит где упало, после починки (git add -p, git commit --ammend) можно запустить git rebase --continue. Тоесть мы фиксим коммит с помошью git commit --ammend.

#### git push --force

После git rebase нужно залить изменения на сервер, у коммитов новые хэши. Если другой пользователь также поменял эту ветку и залил её на сервер обычный push упадёт с ошибкой т.к. версии разошлись а git push --force сотрёт его изменения.

git push --force-with-lease  запушит ветку только если на сервере нет ничего нового (новых коммитов)

git push --force-with-lease --force-if-includes проверяет нашу ветку на то, что в неё включены все скаченные коммиты с сервера. Это своего рода проверка чтобы не затереть чужой код.
