
Для защиты репозитория прибегают к следующим ограничениям:
1. Запрещают заливать коммиты в ветку напрямую, только через MR   
2. Через MR можно залить изменения только если pipeline прошёл успешно, закрыты все треды ревью и есть специальные права на merge.
3. Иногда на конкретные части кода (например модули) отвечают определённые лица, т.е. так называемые CODEOWNERS без апрува которых merge нельзя сделать. В корне репозитория за это отвечает специальный файл`CODEOWNERS`, например такой где определённой папке соответсвует свой CODE OWNER где для пить указаны авторы, например, для пути /payments/ указаны owners @alice @bob.
4. Иногда нужно завести специальные ограничения чтобы в ветку не пушили секреты, большие файлы и прочие артефакты. Для этого существуют push rules, которые есть только в gitlab. Через config можно задать только базовые ограничения - не пушить напрямую в ветку, запретить удаление веток и т.д. Более сложные ограничения - это по сути bash скрипты на gitlab.
5. Серверные проверки выполняются когда код уже запушен поэтому туда могут попадать ошибки и кривой код. Для этого можно настроить клиентские хуки, чтобы они выполнялись на клиенте при коммите, пуше. Например, проверка форматирования, проверка сообщений коммита, прогон тестов.  Лежат эти хуки в папке .git/hooks (он не коммитится). Включить хуки можно командой - `git config core.hooksPath .githooks`.
   Выключить командами - `git commit --no-verify`, `git push --no-verify`
   Например, такой хук ищет TODO и запрещает делать коммит 
	`#!/bin/bash`
	`\# файл .githooks/pre-commit`
	
	`\# берём только то, что в индексе (staged), проверяем добавленные строки`
	`if git diff --cached | grep -E '^\+' | grep -qE 'console\.log|debugger'; then`
	  `echo "Убери отладочный вывод перед коммитом"`
	  `exit 1`
	`fi`
6. Для стандартизации клиентских хуков используют фреймворки `pre-commit`, `lefthook`, `husky`, которые ставят одинаковые хуки для всей команды. Они читают специальные файлы и создают клиентские хуки. Но такие хуки по - прежнему можно отключить.
7. Так как автора коммита легко подделать, указав то же самое имя и email иногда настраивают репозиторий так, чтобы коммиты подписывались ключом. Локально это можно сделать через настройки:
   `git config --global gpg.format ssh //выбор формате ssh, gpg
   `git config --global user.signingkey ~/.ssh/id_ed25519.pub` //сам публичный ключ
   `git config --global commit.gpgsign true    # подписывать все коммиты автоматически`
   На сервере тоже нужно указать свой публичный ключ, включить соотвествующую опцию о запрете пуша без ключа или через pre-receive хук.
8. Что делать если секрет попал в репозиторий? Сначала нужно его отозвать, дальше вычистить из репозитория. Первым делом вычищаем его из всех коммитов:
   git filter-repo --path secrets.env --invert-paths, где --invert-paths - говорит оставить все файлы кроме файла "secrets.env". 
   Это делается локально, затем делаем `git push --force --all` и `git push --force --tags`. Далее коллеги должны заново склонирвоать репозиторий через git clone, т.к. через git pull стягиваются новые коммиты и в ситоге секрет останется в их репозиториях. Ну и в конце нужно почистить MR/PR через поддержку.
9. Ловить утёкший секрет - долго и сложно. Поэтому лучше настроить pre-commit хук, который бы ловил секреты (например через gitleaks), на сервере можно настроить push protection (GitHub). В gitlab проверка уже встроена или через github actions.
