Нужны для того, чтобы блокировать доступ к таблице/строке  на случай если две разных транзакции пытаются изменить данные одновременно, например, уменьшить balance на 100. Если бы блокировки не было, то обе транзакции прочитали бы одинаковый баланс и сделали бы два раза один и тот же запрос, то есть баланс стал бы - 100 а не -200. Для того чтобы изменения были последовательны нужны блокировки. 
###### Строчные блокировки

1. SELECT FOR SHARE - запрещает другим транзакциям UPDATE/DELETE изменять строку, но позволяет делать FOR SHARE другой транзакции.
   
 2. SELECT FOR UPDATE. Её можно использовать явно чтобы заблокировать значение ещё до обновления. Запрещается даже SELECT FOR SHARE
    
3. UPDATE/DELETE - эксклюзивная блокировка, которая блокирует изменение.  Остальные UPDATE/DELETE ждут. Используется по умолчанию в операциях UPDATE, DELETE. 

###### Табличные блокировки

- ACCESS SHARE 
  Нужна для того чтобы во время SELECT в таблице невозможно было изменить её структуру, например, добавив столбцы  или вовсе дропнуть её. И наоборот, пока ALTER TABLE изменяет таблицу, никто из читателей не должен был её читать. Для этого используется блокировка ACCESS SHARE.
  
- ROW EXCLUSIVE
  Операции UPDATE/DELETE/INSERT ставят другую блокировку на таблицу - это ROW EXCLUSIVE. Она также не даёт изменить стрктуру таблицы и не даёт построить индекс, так как опасается, что в индексе будут невалидные данные. Если на таблице уже есть блокировка SHARE, то транзакция встанет в очередь и не будет выполнена прямо сейчас.
  
- SHARE. Используется для построения индекса. Если в этот момент времени установлена ROW EXCLUSIVE (обновление таблицы), то она будет ждать пока эта блокировка исчезнет. Совместима с ACCESS SHARE, то есть создание индекса может работать вместе с SELECT.
  
- SHARE UPDATE EXCLUSIVE блокирует DDL операции, которые сами берут эту блокировку SHARE UPDATE EXCLUSIVE, но разрешает чтение и запись. 
  Например, построение индекса через CREATE INDEX CONCURRENTLY (это DDL операция) ставит блокировку SHARE UPDATE EXCLUSIVE, которая разрешает SELECT/UPDATE/DELETE но блокирует другие операции DDL. 
  
  Сначала делаем Seq Scan, затем механизм убеждается, что нет активных транзакций на таблицу и далее накатывает изменения.
  
- ACCESS EXCLUSIVE нужна для того, чтобы ALTER TABLE, DROP, TRUNCATE отработали корректно. Конфликтует абсолютно со всеми видами блокировок т.к. меняет всю таблицу (колонки, типы, таблицу целиком). Любая операция, читающая старую версию таблицы получила бы невалидный результат. 

Также существует пользовательская блокировка Advisory lock, которая устанавливает блокировку на каком - то объекте. Если две операции используют "SELECT pg_advisory_lock(12345);", то одна из них будет ждать другую. Это часто используется для того, чтобы несколько cron задач или транзакций не работали одновременно с таблицей.

Работает на уровне соединения (`pg_advisory_lock`)  и на уровне транзакции (`pg_advisory_xact_lock`).  Если использовать пул соединений, то блокировка  pg_advisory_lock будет некорректно работать в режиме transaction pooling mode т.е. когда соединение даётся только на время одной транзакции. Таким образом один клиент берёт соединение  в рамках одной транзакции, ставит на него блокировку, выполняет транзакцию и возвращает обратно, блокировка привязана к соединению и всё ещё висит в нём. Другой клиент может взять это же соединение с уже имующейся блокировкой и это как раз утечка блокировок.
