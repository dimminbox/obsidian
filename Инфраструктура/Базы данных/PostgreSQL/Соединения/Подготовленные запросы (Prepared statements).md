
Обычно один и тот же запрос вызывается несколько и планировщик всякий раз строит план под него. Но это можно изменить через оператор PREPARE:

`PREPARE get_shipment (bigint) AS SELECT * FROM shipment WHERE id = $1;` 
`EXECUTE get_shipment(123);` 
`EXECUTE get_shipment(456);`

или на уровне протокола (Extended Query Protocol) , который парсит sql, делает prepare и дальше делает bind c параметрами когда имя задаётся самим драйвером (это проблема). 

В этих случаях планировщик берёт уже подготовленный ранее план запроса чтобы не тратить время на сбор плана.

Драйвер Npgsql придумывает имена(строка s1,s2) для prepared statement. Может быть, что произойдёт ситуация когда для какого - то запроса npgsql сгенерирует номер для prepared statement, который уже есть в этом соединение. Это может случится только в transaction pooling mode когда соединение передаётся между клиентами, в этом случае разные npgsql (по сути разные приложения - клиенты) будут генерировать имена для prepared statement в одном адресном пространстве. В этом случае произойдёт ошибка.
