Для конкурентного доступа к данным Postgres не опирается на блокировки между читателями и писателями, он использует механизм MVCC (Multi-Version Concurrency Control) - механизм многоверсионного управления конкурентным доступом к данным.
###### Чистка старых данных

При изменениях данных старые данные не удаляются, они помечаются как старые версии.  Возникает ситуация когда этих старых версий данных становится очень много и их необходимо чистить. Для этого запускается два процесса -  Autovacuum launcher, который решает каким таблицам нужна чистка, autovacuum workers - процессы, которые запускаются под каждую таблицу. Он просто помечает области на диске, которые соотвествовали старым данным как доступные для записи. Файл на диске остатётся того же самого размера.

Автовауум запускает по наступлению условия : количетсво устаревшийх копий должно быть больше `autovacuum_vacuum_scale_factor` (доля от размера таблицы) + `autovacuum_vacuum_threshold` (фиксированное число). По умолчанию autovacuum_vacuum_scale_factor = 0.2 а autovacuum_vacuum_threshold = 50, то есть для таблицы в 1 млн строк автовауум сработал бы после изменения 200050 строк. Как мы видим на больших таблицах такой больше фактор не эффективен т.к. автовауум будет запускать редко и таблица будет раздуваться. Поэтому факто уменьшают чтобы автовауум запускался чаще. Автовауум делает это без блокировки таблиц в фоне.

У каждой строки есть два номера транзакиций: xmin - номер транзакции, которая создала эту строку. xmax - номер транзакции, которая сделала её неактуальный. то есть. На примере UPDATE:
- Старая версия строки: `xmin=5` (кто создал), `xmax=10` (кто заменил) — мёртвая.
- Новая версия строки: `xmin=10` (та же транзакция, что заменила старую), `xmax` пустой — живая, актуальная.

Autovacuum берёт версию строки и дожен понять по ней что с ней делать - помечать как доступную для записи (то есть это мёртвые данные) либо пропустить (живые данные). 

Но бывает так что в один и тот же момент времени существует и старая вресия строки xmin !=0, xmax !=0 и новая версия строки xmin = xmax старой строки и xmax = 0  и встаёт вопрос какая из версий строк - актуальная? Это может случится при уровне изоляции Reperatable Mode (на этом уровне делает снепшот всех данных). Например, первая транзакция прочитала данные, вторая эти данные изменила. Казалось бы, у нас есть версия строки с xmax !=0 и мы можем её зачистить, но мы не можем этого сделать, т.к. мы должны убедится, что нет активных транзакций, которые используют эту мёртвую версию строки. Для этого он смотрит - используется ли эти старые данные какой - то транзакцией, если да - то просто пропускает их до следующего прохода.

Далее он пишет информацию о том, что на конретной странице есть столько то свободного  места  чтобы в следующий раз не лопатить все страниц одной таблицы. Это структура называется FSM. Он полезен если таблица большая и состоит из многих страниц.

###### Обновляет карту видимости для index-only scan

Когда в Postgres прихоит запрос нужно понять откуда брать данные. Допустим, что для некоторой таблицы есть индекс, индекс по сути это указатель на строки таблиц, т.е. если у нас есть индекс по колонке Price, то он будет содержать ссылки на строки таблиц, которые соотвествуют значениях price в индексе. Бывает так, что в запросе SELECT указаны лишь те колонки, которые и так есть в индексе и поэтому обращаться к таблице нет никакой надобности, но на самом деле это не так потому что существуют ещё и стрые версии строк (которые чистит avtovacuum) и без обращения к таблице невозможно узнать какие данные мёртвые а какие живые. Но что, если бы мы заранее знали, что в данной таблице нет старых версий строк, это бы позволило СУБД не обращаться к таблице а использовать только индекс и поэтому сократило бы время выполнения запроса. 

Именно такую задачу решает avtovauum обновляет специальную структуру - visibility map, которая содержит инфомацию - есть ли в данной странице таблицы мёртвые данные. Если нет, то нет никакой необходимости обращаться к таблице.

###### Freeze

Запрос SELECT всегда идёт в рамках какого - то [[Уровни изоляции транзакций]] у которого всего есть какая - то граница. У уровня read commited эта граница устанавливается в начале каждого SQL запроса т.к. она учитывает изменения других транзакий, которые выполняются параллельно. 

Разберём Read Commited. Открывается транзакция,  в рамках неё есть запрос SELECT. Она должна понимать какие данные для неё доступны, если xmax !=0 и имеет номер транзакции, которая закомиччена, то транзакция считает, что это мёртвые данные. Но если транзакция откачена, то насмотря на xmax != 0 это всё ещё живые данные.

Если xmax =0, то мы должны выяснить по xmin закомиччна ли транзакция, обращаясь к журналу транзакций  и сранивания номера транзакций.
Если она она была закомиччена то нам нужно понять закоммитилась ли она до того момента когда стартовал наш запрос или после. Мы проверяем xmin входит в список активных транзакци (сравнивания номера транзакций) на момент выполнения запроса. Если не входит в список транзакций - то берём, если нет - то пропускаем.  

Узкое место, которое может привести к проблемам - это сравнение номеров транзакций т.к. номера транзакций цикличны. Для решения этой проблемы нужен механизм freeze.

Freeze устанавливает специальное значение `FrozenTransactionId` в xmin.  При проверке закомиччена ли транзакция по нему он видит что установлено специальное значение и считает, что транзакция точно была закомиччена и берёт эти данные для запроса. Похожее просходит и с проверкой на то, не является ли xmin активной транзакцией. MVCC понимает что эта строка изменялась давно и просто берёт её принимая как факт что она не принадлежит к активным транзакциям.

###### Обновление статистики для планировщика

Avtovacuum обновляет статистику pg_statistic, которую использует потом планировщик запросов.  Планировщику запросов  нужно знать использовать ли индекс или таблицу. Если индекс возвратил несклько значений, то нужно брать его если же он возвратил много значений, то проще прочитать таблицу.

Планировщик опирается на гистрограмму значений, которую собирает механизм ANALYZE, которую запускает avtovacuum. А именно он собирает следущие значения:
- общее число строк в таблице. Если их мало, то можно просто прочитать таблицу.
- гистрограмма распределения значений. все значения разбиваются на корзины.  Количество элементов определяется исходя из количества корзин (по умолчанию 100).
- список самых частых значений, т.к. гистограмма плохо работает на "перекошенных" данных, например, если все данные, например, имеют status = active or inactive. Он хранит точную долю строк, которые содержат эти  частные значения.
- Учитывая что большинство строк содержит самые популярные значения, делается допущение, что остальные строки примрено равномерно распределны по остальным уникальные значениям.  Это можно назвать хвостом значений, которое может дать примерное количество строк с этим уникальным и НЕпопярным значением.
