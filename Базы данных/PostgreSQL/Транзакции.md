Уровни изоляции транзакций

1. Read Uncommitted допускает проблему dirty read (грязное чтение). Даже не зафиксированные изменения видны всем потокам.  Проблема грязного чтения возникает, когда один поток пишет данные но ещё не зафиксировал их, второй уже видит новые данные, потом первый откатывает изменения а второй продолжает работать с неверными данные. Это самый грязный уровень но зато самый быстрый.
   
   2. Read Commited - читатели видят только зафиксированные данные. В рамках одной транзации мы видим самые свежие, т.е. закомиченные изменение. Казалось бы, что оперировать всегда свежими данными - правильно, однако бывают ситуации, когда это не так. Например:
   
   `BEGIN TRANSACTION;`
   
	`SELECT balance FROM accounts WHERE id = 1;  -- видим 100`
	`-- программа на основе 100 решает: "баланс достаточный, спишем 50"`
	
	`-- в этот момент другая транзакция списала 80, баланс стал 20`
	
	`UPDATE accounts SET balance = balance - 50 WHERE id = 1;`
	`-- баланс становится -30, хотя проверка вроде бы прошла`
	
	`COMMIT;`
   

3. Repeatable Read решает проблему разных результатов при чтении, которая возникает в  Read Commited. Достигается это с помощью двух разных способов: 
   -  Для каждой транзакции создаётся снимок где для читателей нет блокировок, они просто читают данные из этого снимка. При записи писатели блокируют только писателей.
   - Блокировки строк, т.е. транзакиция блочит строку где было 100.
   
   Но этот уровень транзации не защищает от ситуации когда не будут учтены новые строки, например, заказов было 2 но потом писатель добавил ещё один заказ. В снимке только существующие строки, новых строк там нет. То есть здеь идёт просто рассинхрон.
   
4. Для решения предыдущей проблемы нужен Serializable. При записи он блокирует не только одну строку но и диапозоны, которые высчитываются исходя из кода. Т.е. если есть такой запрос SELECT COUNT(*) FROM Orders WHERE Amount > 100, то никто не может вставлять строку где amount больше 100 пока транзакция не завершится.
